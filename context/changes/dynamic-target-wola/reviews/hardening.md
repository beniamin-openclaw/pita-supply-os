# Adversarial Hardening Review — `dynamic-target-wola`

Scope reviewed: `plan.md`, `change.md`, `research.md`; `supply-os-v1/app/main.py`, `suggestion.py`, `config.py`, `sheets.py`, `supabase_backend.py`; `frontend/src/pages/captain-mp/**`; `frontend/src/pages/manager/**`; `tests/conftest.py`, `tests/test_main.py`, `tests/test_orderable_active_filter.py`, `tests/test_captain_submit.py`; `docs/pita-supply-os-v1/seed/{suppliers,location_product_settings}.csv`; `context/foundation/lessons.md`. The engine (`dynamic_target.py`) does not exist yet — findings about it are risks in the *spec*, verifiable against the plan's own wording and the real seed/prod numbers.

---

1. **Gyros/Souvlaki dynamic target will exceed the static `max_stock_qty_base` on essentially every order — the over-MAX and >25% deviation reason-gates fire by default on the highest-priority Pago SKU.**
   - Trigger: any Wola Captain orders Gyros (P024) via Pago once the flag is on and usage rows are seeded.
   - What the user sees: a reason picker is forced on almost every Gyros order, whether stock is counted or not — the exact "friction" this feature is supposed to remove.
   - Evidence: `docs/pita-supply-os-v1/seed/location_product_settings.csv` — `WOLA__P024,...,min=2,max=10,target=10`. `research.md` — Gyros usage = 12.75 kg/day (confidence A). With Pago's *current* calendar (`delivery_days=Tue`, single weekday — `docs/pita-supply-os-v1/seed/suppliers.csv`), `horizon_days = next_delivery_date([Tue], delivery_date) - delivery_date ≈ 7`. `target_dynamic ≈ 12.75 × (days_until[0..6] + 7) + max(min=2, 12.75) ≈ 100–180 kg`, i.e. 10–18× the current `max_stock_qty_base = 10`. `main.py::_evaluate_submit_line` uncounted-branch checks `order_base > setting.max_stock_qty_base` (unchanged, static) → any order sized to the new suggestion trips the over-MAX gate; counted branch's `delta_pct = |final − suggested| / suggested` will read ~-85%+ if a Captain orders the habitual ~10 kg against a ~100 kg suggestion → trips the >25% deviation gate too. Plan explicitly leaves `max_stock_qty_base` unchanged ("What We're NOT Doing") and only proposes a *raise* in `prod-sql.sql` section D, marked "optional."
   - Severity: **CRITICAL**.
   - Hardening: make the max-ceiling raise (section D) a *mandatory* co-requisite of enabling dynamic target for any row, not optional — either gate `resolve_effective_target` on `max_stock_qty_base ≥ target_dynamic × k` (else fall back to static, reason `max_too_low`), or scope the initial rollout to rows where the current max already comfortably covers the computed horizon (verify Gyros/Souvlaki/Pita numerically before enabling — Coca-Cola/Zero are safer). Add a test asserting `resolve_effective_target` never returns `mode="dynamic"` when `target_dynamic > max_stock_qty_base` without an explicit acknowledgment.

2. **`min_stock_qty_base` — never audited because it was purely cosmetic — silently becomes the dominant term of the safety floor for slow-moving Coca-Cola SKUs.**
   - Trigger: Coca-Cola / Coca-Cola Zero dynamic target computation.
   - What the user sees: nothing obviously wrong — badge says "dynamiczny · A" — but the suggested quantity is driven by a stale guess, not by measured usage.
   - Evidence: `location_product_settings.csv` — `WOLA__P068 min=24,max=120,target=96` — annotated `"ESTIM - verify after first order cycle"`. `research.md` — P068 usage = 4.53 szt/day (confidence A). `safety_base = max(min_stock_qty_base, usage_per_day × safety_days) = max(24, 4.53) = 24` — the untouched, never-verified `min` (5.3 days of usage) swamps the actual measured daily rate (1 day). `research.md` item 3 acknowledges "min finally does something" but the plan has no audit/verification step for these 18 rows' `min` values before flipping the switch, contradicting `context/foundation/lessons.md` "Master-data ops: diff before, audit after."
   - Severity: **HIGH**.
   - Hardening: before enabling dynamic target per row, audit `min_stock_qty_base` against the seeded `usage_per_day_base × safety_days` and flag/clear the `"ESTIM..."` rows that don't reconcile; alternatively cap `safety_base` contribution from `min` (e.g. `min(min_stock, usage × N days)`) so a stale min can inflate but not dominate arbitrarily.

3. **Section C (supplier calendar fix) is labeled "optional," but without it the horizon math for Pago is silently ~1.75× too large (weekly instead of the real twice-weekly Tue+Sat cadence) — and Coca-Cola cannot go dynamic at all.**
   - Trigger: operator applies migration 0017 + usage rows (mandatory, section A+B) but skips the "optional" calendar update (section C).
   - What the user sees: for Pago, a confidently-labeled "dynamiczny · A" target computed from the *wrong* delivery cadence, over-ordering by design (see #1, compounding it). For Coca-Cola, nothing changes at all — `delivery_days='TBD'` is unparseable, so `resolve_effective_target` always falls back to static (`reason=no_calendar`), silently defeating the change's own scope/success-criteria ("Coca-Cola / Zero cards" showing dynamic math, per plan §Desired End State and Manual Verification).
   - Evidence: `research.md` prod facts table — `Pago calendar in master data | delivery_days='Tue'... (GoStock PZ: Tue + Sat)`; `Coca-Cola calendar in master data | TBD / TBD (GoStock PZ: Thu)`. Plan §Desired End State lists the calendar as one of three *required* gating steps ("(c) the supplier calendars are set"), while §Phase 4 lists the same calendar SQL as "section C (optional)". Internal contradiction.
   - Severity: **CRITICAL** (silent over-ordering risk) / documentation bug that makes it likely to be skipped.
   - Hardening: reclassify section C as mandatory alongside B, or make `resolve_effective_target` refuse to activate for a supplier whose calendar has fewer weekly delivery days than its GoStock-observed cadence (not detectable in code, so at minimum: strongly-worded, non-optional prod-sql step, and a plan-review checklist item requiring section C applied before section B for Pago).

4. **`captain_order_edit` gate parity is broken by the existing "feedback r6" full-orderable-list merge in `OrderEditPage.tsx` — the edit screen shows a freshly recomputed (today's) dynamic target for every still-orderable product, not the frozen order-line snapshot the plan assumes.**
   - Trigger: a Captain (or a Manager send-back) reopens an order for edit more than a few hours/a day after original submission — normal for the send-back flow ("Odrzuć do poprawy").
   - What the user sees: card shows green/no-reason-needed based on today's target; on Save the backend 400s ("Line ... deviates X% from suggestion without reason_code") because it gates against the *original* snapshot target — or the reverse (FE shows red/forces a reason the backend wouldn't have required). This is precisely the "Captain hits a 400 at 13:58 before cutoff" failure mode.
   - Evidence: `frontend/src/pages/captain-mp/OrderEditPage.tsx:112-138` — `lineToItem` builds snapshot-based items, but the subsequent `api.orderable(data.supplier_id)` call (lines 128-139) **replaces** every item still present in the fresh orderable response (`setItems([...orderable, ...missing])`); only products no longer orderable keep the snapshot-derived item. Plan §Phase 2 states: "captain_order_edit: ... effective_target = existing_line.target_stock_qty_base when the product was on the original order ... Rationale: the edit screen renders the snapshot target, so the gate must use it." — that rationale is false for this codebase as it stands: the edit screen does **not** render the snapshot target for any product still orderable, because of the r6 merge. `main.py::_build_orderable_items` (called by `/api/captain/orderable`) always resolves with `requested_delivery_date=None` per plan, i.e. "today," which will differ from the order's original delivery date once time has passed.
   - Severity: **CRITICAL** (silent, everyday-path FE/BE divergence, not an edge case).
   - Hardening: either (a) have `OrderEditPage` request the orderable list with a query param signalling "use snapshot targets for lines on this order" (server merges frozen values back in for lines present on `data.lines`), or (b) have the FE overlay `line.target_stock_qty_base`/`target_source` from the order snapshot onto the fresh orderable item for any product_id already on the order, instead of taking the orderable response verbatim. Add a test: edit an order the day after submission with a changed `today` and assert FE-computed state and backend gate agree.

5. **`captain_submit`'s deviation/over-MAX gates now trust a client-computed `requested_delivery_date` to determine the audit-of-record target — a field that was previously inert metadata.**
   - Trigger: every normal Captain submit (`CaptainMP.tsx:518` always sends `requested_delivery_date: getRequestedDeliveryDate(supplier.delivery_days)`), not just an edge case.
   - What the user/attacker sees: the gate boundary is now a function of a value computed entirely client-side, with no server-side sanity check beyond "clamp `days_until_delivery ≥ 0`" (plan). A clock-skewed device, a stale tab kept open across midnight, or a deliberately crafted payload with a far-future `requested_delivery_date` inflates `days_until_delivery`/the resulting target arbitrarily, which can silently widen or narrow the deviation-gate boundary (either bypassing the "reason required" gate for an unusually large order, or forcing an unnecessary reason for a normal one).
   - Evidence: `frontend/src/pages/captain-mp/lib/dates.ts::getRequestedDeliveryDate` uses `new Date()` (browser-local, no Europe/Warsaw conversion, unlike backend `_WARSAW_TZ`/`_today_warsaw()`), no cutoff logic, offsets 1..14. `models.py::CaptainSubmitRequest.requested_delivery_date: Optional[date]` has no bounds (`ge`/`le`) at all. Plan: "delivery_date = requested_delivery_date if given (clamped so days_until_delivery ≥ 0)" — no ceiling clamp mentioned.
   - Severity: **HIGH** (everyday path, real gate-integrity impact; not remote-exploit-grade since only a Captain's own order is affected, but it undermines the >25%/critical-under gates the whole product exists to enforce).
   - Hardening: (a) cap `requested_delivery_date` server-side to a sane window (e.g. reject/ignore values >14 days out, matching the FE's own 1..14 day search window); (b) recompute/validate that the client's `requested_delivery_date` actually matches a real next-delivery-weekday from `supplier.delivery_days` before trusting it for target math, falling back to the server's own `next_delivery_date(weekdays, today)` on mismatch; (c) compute `today` for the horizon math from `_today_warsaw()` server time only, never influenced by anything the client sends beyond the (validated) `requested_delivery_date`.

6. **Uncaught `ValueError` from `suggestion.compute_suggestion` when a dynamic target is negative/NaN — one bad usage row can 500 an entire Captain order submit.**
   - Trigger: a malformed or badly-entered `location_product_usage` row (negative `usage_per_day_base`, or a computation bug in `dynamic_target.py`) produces a negative target for one product on a multi-line order.
   - What the user sees: 500 Internal Server Error on `/api/captain/submit` for the *whole order* (all lines, all products), not just the offending one — the Captain cannot submit anything for that supplier at all, with no actionable message.
   - Evidence: `suggestion.py::compute_suggestion` calls `_validate_finite_nonneg("target_stock_qty_base", ...)`, which raises `ValueError` on negative/NaN/inf. `main.py::_evaluate_submit_line` calls `compute_suggestion(...)` directly inside the per-line loop of `captain_submit`/`captain_order_edit` with **no try/except** (only the separate `/api/captain/suggest` endpoint catches `ValueError`). The plan's `LocationProductUsage.usage_per_day_base: float` has no documented `Field(ge=0)` constraint, and `resolve_effective_target`'s gating on "usage > 0" is a design intent, not yet code — its exact boundary condition (`> 0` vs truthy) is unverified.
   - Severity: **CRITICAL** (single bad data row takes down submit for an entire order; matches the repo's documented pattern of "one bad row costs everyone" — cf. lessons.md's droplet/stale-CSV precedent).
   - Hardening: add `Field(ge=0)` to `usage_per_day_base` and `safety_days`/`safety_base` in the model; wrap the `compute_suggestion` call site in `_evaluate_submit_line` (or `resolve_effective_target`'s output) with a defensive `try/except ValueError` that degrades that *one line* to the static target and logs, never bubbling to a 500; add a test with a deliberately negative/NaN usage row asserting submit still returns 200 (degraded to static) rather than 500.

7. **`_load_usage_safe`-style degrade risks repeating the exact `except WorksheetNotFound`-only mistake this codebase has already been bitten by twice.**
   - Trigger: code deployed before migration 0017 lands on Supabase, or the Sheets legacy backend without the `location_product_usage` worksheet.
   - What the user sees: on Supabase, a missing table raises `sqlalchemy.exc.ProgrammingError` (wrapping `UndefinedTable`), not `sheets.WorksheetNotFound` — if the new helper is (mis)written by analogy to older, now-fixed helpers' first draft, every orderable/submit request 500s until the migration lands.
   - Evidence: `main.py`'s own docstrings for `_load_inventory_events_safe` and `_load_transport_events_safe` explicitly document this exact bug and its fix ("Catching only `WorksheetNotFound` ... was a Sheets-shaped assumption ... on Supabase an absent table raises a SQLAlchemy `ProgrammingError` instead ... turned the entire route into a 500 ... exactly the deploy-ordering window the migration is most likely to be read in"). `supabase_backend.py::_fetch_all` runs `conn.execute` unguarded inside a bare `with _get_engine().connect()`.
   - Severity: **HIGH** (repeat of a documented, previously-shipped bug class; deploy-ordering is explicitly a live prod concern here per `migration Notes`).
   - Hardening: `_load_usage_safe` must catch bare `Exception` (matching the *fixed* versions of the two sibling helpers), not a backend-specific exception type. Add one test per backend (seed/sheets/supabase) simulating the table/worksheet/file missing and asserting the orderable route still returns 200 with static targets.

8. **Existing regression test `test_orderable_active_filter.py` will break — or worse, get "fixed" by adding a silent best-effort supplier lookup that masks a real prod misconfiguration — because `_build_orderable_items` gains a hard new `backend.load_suppliers()` dependency.**
   - Trigger: implementing Phase 2 exactly as described.
   - What the user sees (if fixed carelessly): a location/supplier combination whose backend fake or real caller can't resolve a supplier row silently reports "no calendar" and falls back to static everywhere, masking a genuine data problem (e.g. a supplier row deleted/renamed) as "just not dynamic yet."
   - Evidence: `tests/test_orderable_active_filter.py:19-31` — `_Backend` stub defines `load_products`, `load_supplier_products`, `load_location_product_settings` only, **no `load_suppliers`**; it is passed directly to `_build_orderable_items(backend, "WOLA", "SUP_PAGO")` at lines 79/90/104/105/115 (bypassing `_choose_backend()` entirely). Plan §Phase 2: "`_build_orderable_items(backend, location_id, supplier_id)`: loads suppliers + usage once, passes them down" — a hard new call to `backend.load_suppliers()` that this existing, currently-green regression test (guarding a real historical production bug — Feta/Tirokafteri/Tzatzyki) does not stub.
   - Severity: **HIGH** (guaranteed CI break if unaddressed; latent correctness risk if "fixed" the wrong way).
   - Hardening: update `test_orderable_active_filter.py`'s `_Backend` to add `load_suppliers`, and make the supplier lookup fail loud in `_resolve_master_data`-style code paths (400/well-defined error) while making it fail-soft (degrade to static) *only* in the specific `_build_orderable_items` path used for display, with an explicit code comment distinguishing the two so a future reader doesn't conflate "no supplier row" with "no calendar."

9. **A single malformed row in the whole `location_product_usage` table silently disables dynamic targeting for *every* product/location, not just the bad row — with only a log line as evidence.**
   - Trigger: one bad CSV/SQL row (e.g. blank `usage_per_day_base` cell coerced to `None` where the model has no default) fails Pydantic construction while the loader builds the full list.
   - What the user sees: nothing — every product silently reverts to static targets, indistinguishable from the flag being off, and no one but a log-tail knows why.
   - Evidence: `seed_loader`/`sheets` row-construction pattern elsewhere in this codebase (e.g. `sheets._read_with_ttl`) raises on the first bad row for the *whole worksheet* rather than skipping it; plan's `_load_usage_safe` "catches ANY exception ... returns `{}`" — a table-wide catch, by design, per the plan's own wording.
   - Severity: **MEDIUM** (safe direction — fails closed to static — but a repeat of the exact "silent failure invisible except in logs" pattern `lessons.md` calls out repeatedly).
   - Hardening: make the CSV/SQL loader tolerant per-row (skip and log the one bad row, keep the rest), not per-table; expose a `/health/internal`-visible count of loaded usage rows so a broken batch is detectable without grepping logs.

10. **Unbounded Sheets/network calls (or at minimum warning-log spam) on every orderable/submit request at every non-Wola location, because nothing in the plan gates the `load_location_product_usage()` call behind the kill switch.**
    - Trigger: `SUPPLY_OS_DYNAMIC_TARGET_ENABLED=false` (test default, or a prod rollback) but `_build_orderable_items`/`_evaluate_submit_line` still unconditionally calls `backend.load_location_product_usage()` before consulting the flag.
    - What the user sees: no functional bug (falls back to static either way), but every sheet-mode captain-submit test (`tests/test_captain_submit.py`, which patches `sheets.load_products/suppliers/supplier_products/location_product_settings` but *not* `load_location_product_usage`) triggers a real `sheets._sheet()` call — fast-failing with `RuntimeError("google_sheet_id is empty")` given blanked test creds, but that's an accidental safety net, not a design guarantee — and in prod, every single order at every location other than Wola pays an extra, pointless Sheets/Supabase read.
    - Evidence: `tests/test_captain_submit.py:363-465` mock four loaders per test, omitting the new one; `tests/conftest.py` blanks `SUPPLY_OS_GOOGLE_SHEET_ID` (documented purpose: "the suite NEVER touches the live Google Sheet") — a design principle this new code path risks violating in spirit even if it fails fast today.
    - Severity: **MEDIUM**.
    - Hardening: check `settings.dynamic_target_enabled` *before* calling `backend.load_location_product_usage()` at all (short-circuit to `{}` without touching the backend), both in the route wiring and inside `_load_usage_safe`; add an explicit test asserting the usage loader is never called when the flag is off.

11. **`resolve_effective_target`'s frontend/backend `next_delivery_date` computations for `requested_delivery_date` disagree at the day boundary — the numeric-`delivery_days` case is a live latent divergence, not yet triggered but one master-data edit away.**
    - Trigger: any future supplier configured with a purely numeric `delivery_days` (e.g. `"3"`, meaning "every 3 days" in the FE's interpretation) that also gets a `location_product_usage` row.
    - What the user sees: FE (`dates.ts::getRequestedDeliveryDate`) treats a numeric string as "N days from today"; backend `_parse_weekdays`/`parse_delivery_weekdays` (moved to `dynamic_target.py` per plan) has no numeric-token branch — it splits on separators and looks up each token in `WEEKDAY_MAP`, so a numeric token fails every lookup and the whole calendar is "unparseable" → the *engine* falls back to static (`reason=no_calendar`) regardless of the FE's own guess. Currently fails safe (no numeric `delivery_days` exists in `suppliers.csv` today), but the divergence between the two interpretations is real and pre-existing, and now sits directly on the path that decides whether a target is trustworthy.
    - Evidence: `frontend/src/pages/captain-mp/lib/dates.ts:20-24` vs `main.py::_parse_weekdays` (current) / plan's `parse_delivery_weekdays`.
    - Severity: **LOW** (currently inert, fails safe).
    - Hardening: either teach the backend calendar parser the same "N days" numeric convention the FE already uses, or actively reject/normalize numeric `delivery_days` values at data-entry time so the two never need to agree. Add a test asserting a numeric `delivery_days` always resolves to static (documented behavior, not accidental).

12. **`ceil_unit`'s inventory-unit-based rounding ("0.1 for kg, whole unit otherwise") is a second, independent rounding pass that can disagree with the SKU's own `rounding_rule` (`half_allowed`, etc.), compounding minor granularity mismatches into the visible target.**
    - Trigger: any szt/opak product whose `SupplierProduct.rounding_rule` is `half_allowed` (fractional purchase units legitimate) — `ceil_unit` still forces the *target* itself to a whole inventory unit before the purchase-unit rounding is applied a second time downstream.
    - What the user sees: a target that's "rounder" than the SKU's own granularity would otherwise allow — cosmetic in most cases, but worth a unit test since it's a second, product-agnostic rounding layer bolted in front of the existing per-rule one.
    - Evidence: plan §Phase 1: "`ceil_unit(value, inventory_unit) -> float`... rounds up to 0.1 for `kg` and to a whole unit otherwise" — keyed on `inventory_unit`, not on `rounding_rule`.
    - Severity: **LOW**.
    - Hardening: document explicitly in `dynamic_target.py` that `ceil_unit` rounds the *base-unit* target only (never the final purchase-unit suggestion, which still goes through `_round_per_rule`), and add a test crossing a `half_allowed` szt product with the dynamic path to confirm the two rounding stages don't produce a visibly "wrong" whole-number target for a product the operator expects to see half-units on.

13. **FR-012 `_aggregate_suggestion_review` roll-up loses meaning once `avg_suggested_qty_purchase`/`avg_abs_deviation_pct` mix days computed against different (dynamic vs static, or dynamic-on-different-days) targets — a real deviation and a "just a different day's target" both look identical in the average.**
    - Trigger: any Wola Coca-Cola/Pago product with 2+ order-line rows once dynamic targets are live.
    - What the user sees: the owner's suggestion-review screen shows an "average abs deviation" that can no longer distinguish "the engine's suggestion was wrong" from "the target legitimately moved day to day because usage/day or the delivery calendar changed" — undermining the stated purpose of FR-012 ("owner validates Bukat/Coca-Cola suggestions and master data").
    - Evidence: `main.py::_aggregate_suggestion_review` averages `suggested_qty_purchase`/`delta_vs_suggestion_pct` across all `order_lines` rows for a product with no notion of "which target regime produced this row." `order_lines` carries only the numeric `target_stock_qty_base` (per plan, "No new order_lines column... target snapshot is the audit field") — no `target_source`/`mode`/`confidence`/`usage_per_day` is persisted anywhere, so a reviewer looking at a historical line months later cannot reconstruct whether that day's number was dynamic or static, nor what usage rate/calendar state produced it if `location_product_usage`/`suppliers.delivery_days` have since been edited.
    - Evidence (PRD conflict): `context/foundation/prd.md` NFR floor: "Every dispatched order line stays inspectable later — suggested vs captain vs manager values plus reason codes — for coaching and master-data improvement." A bare `target_stock_qty_base` float, once the underlying formula and its inputs are mutable and undated, does not satisfy "inspectable" the way it did when the target was a stable master-data lookup.
    - Severity: **HIGH** (directly conflicts with a stated PRD quality floor; the plan explicitly chose not to add an audit column, calling it out under "What We're NOT Doing" without addressing this conflict).
    - Hardening: at minimum, persist `target_source.mode` (static/dynamic) and `confidence` alongside the existing snapshot on `order_lines` (a narrow addition, not the full `TargetSource` object) so `_aggregate_suggestion_review` (and any future manual audit) can filter/segment by regime; failing that, explicitly document this as a known limitation in `change.md` so the owner doesn't misread FR-012 output during the pilot.

14. **The Manager never sees `target_source` — the Manager reviewing/dispatching a Wola Pago/Coca-Cola order has zero visibility into whether a line's target is dynamic or static, or why it moved from the number they remember.**
    - Trigger: Manager opens `/manager` order detail or the Transport batch grid for a Wola order with dynamic-target lines.
    - What the user sees: `line.target_stock_qty_base` (a plain number) with no badge/math — a Manager who has internalized "Coca-Cola target is 96" sees "43" one day and "112" the next with no explanation, exactly the "learning loop" pain FR-012/US-01 exist to solve, now reintroduced at the Manager layer.
    - Evidence: `frontend/src/pages/manager/OrderLineTable.tsx:162-192` reads only `line.target_stock_qty_base`/`suggested_qty_base`/`suggested_qty_purchase`/`delta_vs_suggestion_pct` from `ManagerOrderLineDetail` — plan §Phase 3 adds `target_source` only to `OrderableItem`/`frontend/src/types.ts`, never to `ManagerOrderLineDetail`/`ManagerQueueItem`/`TransportBatchOrder`.
    - Severity: **MEDIUM**.
    - Hardening: surface at minimum a static/dynamic badge (not the full math) on the Manager order-detail line table and the Transport grid, reusing whatever `target_source.mode`/`confidence` gets persisted per finding #13.

15. **`min_stock_qty_base > 0` "below minimum" UI signal (`ProductCard.tsx`) is now comparing the CURRENT stock against an unrelated static `min`, while the actual gating "safety floor" concept moved into the dynamic target — two different numbers both called "minimum" with different meanings, shown side by side.**
    - Trigger: any dynamic-target product where current stock is below `min_stock_qty_base` but the dynamic target's `safety_base` (which *also* derives from `min_stock_qty_base`) is a much larger number.
    - What the user sees: a "poniżej minimum" red pill using the raw `min_stock_qty_base` (e.g. 24 for Coca-Cola) next to a target/suggestion that already baked that same 24 into its own safety floor — potentially confusing double-counting of the same number in two different UI roles, with no code change flagged in the plan to reconcile or explain it.
    - Evidence: `ProductCard.tsx:88-94` (`belowMin` from `item.min_stock_qty_base`) vs `research.md` item 3 / plan formula (`safety_base = max(min_stock_qty_base, usage_per_day × safety_days)`); plan does not touch `card.belowMin` semantics.
    - Severity: **LOW** (cosmetic/comprehension risk, not a gate bug).
    - Hardening: note this explicitly in the plan's Phase 3 UI section and consider whether "below minimum" should compare against `safety_base` instead of the raw static `min` once a product goes dynamic.

16. **Test-suite order-independence for the new flag relies entirely on the *existing* `tests/conftest.py` — a single misplacement (implementer adds the `setdefault` to a new file, or a test module sets `os.environ[...]` directly instead of via `mocker.patch.object`) silently reintroduces the exact bug `lessons.md` already documents for this repo.**
    - Trigger: implementation adds `SUPPLY_OS_DYNAMIC_TARGET_ENABLED` handling anywhere other than the single existing `tests/conftest.py`, or a new test does `os.environ["SUPPLY_OS_DYNAMIC_TARGET_ENABLED"] = "true"` instead of `mocker.patch.object(settings, "dynamic_target_enabled", True)`.
    - What the user sees: nothing in CI most of the time — the bug is order-dependent, so a full alphabetical `pytest` run can pass while a subset/parallel run (or pytest-xdist reordering) silently makes unrelated tests run with dynamic targets on, producing flaky, unexplainable date-dependent failures days/weeks later as `date.today()`'s real value drifts.
    - Evidence: `context/foundation/lessons.md` "Tests must be order-independent" — documents this exact failure class for this exact settings object (`Settings()` instantiated once at import in `config.py:83`).     - Severity: **MEDIUM** (repo has a documented lesson for exactly this; low probability given the explicit plan wording, but the blast radius if missed is "flaky, hard-to-diagnose test suite," which is disproportionately expensive to debug later).
